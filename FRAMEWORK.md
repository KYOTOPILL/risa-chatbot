# RiSA: how the framework works

RiSA is a Thai-language chatbot that answers staff questions from company documents and sends the files they ask for.
Stack: FastAPI + plain HTML/JS, Chroma vector store, local `bge-m3` embeddings (Ollama), chat model `gpt-5.4-nano` via OpenAI by default; `RISA_CHAT_BASE_URL` + `RISA_CHAT_MODEL` point it at any OpenAI-compatible server (e.g. local Ollama `qwen3:8b`).

## 1. The big picture

```
 content/<topic>/...            (admin uploads, edits, deletes files)
        |
        v
  ingest.build_index  --->  Store (Chroma)
   - extract text (+docx tables,xlsx,pptx) - "docs"  collection: text chunks     (for answering questions)
   - chunk 800/100            - "names" collection: one entry per   (for finding files)
   - embed (bge-m3)             downloadable file = name + Thai summary
   - LLM summary (new files)
        |
        v
  rag.answer(history, message, store)
   LLM + 4 tools  ->  Reply(text, file_doc_ids, sources)
        |
        v
  app/api/server.py  /api/chat/stream  ->  web/app.js shows text as it is written + file names as download links
```

Two ideas carry the whole design:

1. **Two indexes.** Question answering searches the document text. File requests search a separate index of file names plus short Thai summaries, because file names are English and staff ask in Thai.
2. **The LLM routes, code only guards.** The model decides which tool to call. Code validates the result. There are no keyword lists or regex rules for intent.

## Project layout
```
app/core/      config, auth, state (settings, login, shared singletons)
app/api/       server, admin (FastAPI app and the file-manager API)
app/rag/       extract, chunk, ingest, store, rag, docmeta (documents -> index -> answers)
app/features/  tracker, tracker_api, my_requests, downloads, forms_ai, steps_ai
web/           frontend (html, css, js)      tests/ evals/ scripts/ docs/
content/       documents; only the `shareable/` folders are tracked by git
```
Run modules from the repo root: `python -m app.rag.ingest`, `uvicorn app.api.server:app`.

## 2. What was built, in order

| Step | What changed |
|---|---|
| Model | Local LLM replaced by the OpenAI API, cheapest working model (`gpt-5.4-nano`, `reasoning_effort: "none"`). Key lives in `.env`. |
| UI | 20 polish items in `web/` (shortcut hint, skeleton rows, undo toast, view transitions, safe-area, and more). Welcome chips are general questions. |
| Cleanup | Unused Ollama models and RAGAS lines removed. `.env` loader added to `app/core/config.py`. |
| File requests | Files shown as named links, not a button. No asking "which file". List requests send all matches. |
| Name index | Each file gets an LLM-written Thai summary (kept even when downloadable is off); downloadable ones are searchable by it. File search matches name plus summary. |
| Incremental indexing | Only new or changed files are re-embedded and re-summarised. Built for about 500 documents. |
| Topic folders | The first non-`shareable` folder is the file's topic and acts as a soft filter. |
| Tool-based routing | Rules and regexes deleted. The model calls tools. Eval score went from 17/24 to 22/24. |
| Cost cuts | Token usage logging, answer cache for repeated questions, output cap. See section 5. |

## 3. The functions that were added

### `app/rag/rag.py` (the brain)

| Function / constant | Job |
|---|---|
| `answer(history, message, store, llm)` | Runs the tool loop and returns a `Reply`. Everything else supports this. |
| inner `run(name, args)` | Executes one tool call against the store and returns text for the model. |
| `chat_tools(messages, tools, tool_choice)` | One OpenAI call with tool support. `chat()` is the plain version, still used for summaries. |
| `chat_tools_stream(..., on_delta)` | Same call with `stream: true`; answer text goes to `on_delta` as it arrives, tool-call fragments are joined, token usage is still counted. `on_delta(None)` means the text so far was not the answer (a tool call followed). `answer(..., llm=chat_tools_stream, on_delta=...)` streams only the final round, and `_hold_markers` keeps `NOT_FOUND` / `OUT_OF_SCOPE` from showing before they are swapped for the Thai message. |
| `AGENT_SYSTEM` | System prompt in four labeled sections: ROLE, TOOLS, RESPONSE GUIDELINES, FORMAT. The guidelines are the lessons from fixing real answers: answer only the exact thing asked (related is not the same); if documents only cover a related subject, say so and name what does exist; overview questions get one sentence per topic and no file list; the answer never shows file names, number prefixes or extensions: files are described by purpose and, when several match, the user is asked which purpose they need (the file cards and LINE links still carry the real name); direct answer first, lists only for 3+ items, about 8 lines at most; exact numbers; dates only for status questions; `NOT_FOUND` only when nothing relevant exists, `OUT_OF_SCOPE` for off-topic; Thai only, no markdown, polite `ค่ะ`. When a new lesson comes up, add it to the guidelines (and a case to `evals/questions.json`), not a one-off patch. |
| `TOOLS` | The four tool definitions below. |
| `_dedupe`, `_context` | Drop overlapping chunks and format search results with their modified date. |
| `is_mostly_thai` | Detects an English reply so it can be retried once in Thai. |
| `Reply`, `Turn` | Result and history dataclasses. |
| `usage` | Running totals of calls, prompt tokens and completion tokens, filled by `_post` from OpenAI's `usage` field. `evals/run_eval.py` prints it. |
| `_glossary()` | Reads `glossary.txt` (project root, one `term = meaning` per line, `#` lines skipped) and appends it to the system prompt on every answer, so a term the model would translate wrongly (for example `settlement` = first-arrival allowance, not repayment) has a fixed meaning. Edit the file, no restart needed. |
| `MAX_ANSWER_TOKENS` | Output cap (600) sent as `max_completion_tokens` by `chat_tools`. Summaries use `chat()` and are not capped. |

The four tools:

| Tool | When the model uses it | What it returns |
|---|---|---|
| `search_documents(query, topic?)` | Questions about what documents say | Up to `TOP_K=4` chunks, fenced in `<context>`, hits over `MAX_DISTANCE=0.6` dropped |
| `find_files(query, topic?)` | User asks for or asks about a file | Up to `FIND_K=8` candidates as `f1 \| name \| topic \| summary` |
| `send_files(file_ids)` | After `find_files`, to attach files | Confirmation. Only ids from this turn's `find_files` are accepted |
| `list_topics()` | Vague "what documents do you have" | Each topic folder with its file count, file names and short Thai summaries (`Store.topic_files()`), so the bot can summarize what each topic holds and then ask which one |

Guards in code (the model cannot bypass them):
- Round 0 forces a tool call (`tool_choice="required"`). Loop is capped at `MAX_ROUNDS=4`.
- Invented file ids are ignored. At most `MAX_FILES=8` files are sent.
- Thai-only check with one retry, then fall back to the HR contact message.
- Files sent but empty text gives `FILE_READY`. Nothing found gives `NOT_FOUND` (HR contact message). An off-topic question gives `OUT_OF_SCOPE`: "คำถามนี้ไม่เกี่ยวข้องกับเอกสารที่มีอยู่" plus the HR contact. The model decides which, so an office question the documents do not cover can occasionally come back in the model's own words instead of the HR message.
- Search results are wrapped as data, so instructions inside documents are ignored.
- If the model picks the wrong topic, the search also runs across all topics.

### `app/rag/store.py` (the memory)

| Function | Job |
|---|---|
| `Store.update(items, keep)` | Embed only changed docs, delete removed ones. |
| `Store.signatures()` | Returns `size:mtime_ns` per file so unchanged files are skipped. |
| `Store.find_files(question, k, category)` | Searches the `names` collection (name plus summary). |
| `Store.topic_files()`, `categories()` | Topic folders and how many downloadable files each has. |
| `Store.doc_path()` | Maps an id to a path. The server uses it to show file names. |
| `Store.cached_summary(sig)`, `remember_summary(sig, text)` | Summaries remembered by file signature (size + mtime) in `index/summaries.json`. Moving or renaming a file, or switching downloadable off and on, keeps the same content, so it keeps its summary and costs no new API call. `ingest.build_index` reads this before calling the LLM, and `/api/admin/files` falls back to it so a non-downloadable file still shows its description. |
| `Store.summaries(ids=None)` | doc_id to Thai summary for downloadable files. Used by `/api/chat` (file cards) and `/api/admin/files`. |
| `NameHit` | Result row for file search. |

### `app/rag/ingest.py` and `app/rag/docmeta.py` (the intake)

- `build_index(content_dir, store, summarize)` walks `content/`, skips files whose signature is unchanged, and returns `{"indexed","changed","skipped"}`.
- `summarize(text)` asks the model for a Thai summary once for every new or changed file, downloadable or not, and remembers it by file signature, so a description never depends on the downloadable switch. A file whose summary is missing (for example indexed before this rule, or a failed call) is indexed again on the next reindex. Only downloadable files' summaries go into the name index used by file requests. A failure is logged and the file is still indexed.
- `DocMeta` gained `summary` and `sig`.
- `app/rag/extract.py`: `extract_text` reads PDF (pymupdf), DOCX (`_docx`: paragraphs and tables in document order, a table row is one line of cells joined by ` | `, merged cells counted once, nested tables not read), XLSX (`_xlsx`), PPTX (`_pptx`), TXT and MD. `_xlsx` writes one paragraph per row as `[Sheet] Header: value | Header: value` (first non-empty row is the header, empty rows and cells are skipped, at most `MAX_SHEET_ROWS=3000` rows per sheet, cached formula values), so chunking never cuts a row and each value keeps its column name. `_pptx` writes one paragraph per slide: text boxes, tables (cells joined by ` | `), grouped shapes and speaker notes; slides with no text are skipped. Old `.xls` and `.ppt` are not supported (`SUPPORTED_EXTS` in `app/core/config.py`, also the upload picker in `admin.html`). New dependencies: `openpyxl`, `python-pptx`.

### Tracking dashboard (`app/features/tracker.py`, `app/features/steps_ai.py`, `app/features/tracker_api.py`, `web/home.*`)

Goals 2 and 3 of the meeting: step tracking and document check. Open `/`. Spec: `docs/superpowers/specs/2026-11-06-tracking-and-document-check-design.md`.

- `app/features/tracker.py` (`Tracker`, SQLite file `tracker.db`, git-ignored): all rules, no web or LLM code. A type has numbered versions, `draft` or `approved`. `create_submission` needs an approved version and at least one researcher; the submission keeps that version, so editing a type later never changes it. `list_submissions` and `get_submission` return only the researcher's own submissions (staff see all); a foreign id gives `None`. `move_step` is only for the staff in charge, goes forward or back, `to_step == step_count` means done, and every move is logged in `step_events`. `add_upload` / `latest_uploads` keep every upload and treat the newest per document as current. `review_upload(approve|return)` returns `True` when the approved document was the last one of the current step: then it moves the submission one step on by itself. A step with no documents never advances by itself. Step lists are validated (`validate_steps`: non-empty, each step has a title and a documents list). A document that is `sent` or `approved` cannot be uploaded again. `send_upload` and `review_upload` change status only from the expected state, and the auto-advance fires only for the request that still sees the old step.
- `app/features/steps_ai.py`: `draft_steps(pages)` asks the model for a JSON list of steps (`title`, `documents`, `page`, `unsure`) from a scholarship document and raises `ValueError` on anything that is not that shape. The prompt asks for short document names, and `PLACEHOLDER` strips any `{{field}}` the model copies from a template. `screen_document(...)` returns findings of kind `missing`, `incorrect` or `unclear`. `find_template(doc_name)` finds a blank form under `Form template/` by file-name substring. The model is a parameter (default `rag.chat`).
- `app/features/tracker_api.py` (`/api/track/...`): username and password login against `MOCK_USERS` in `app/core/config.py` (demo passwords in plain text); the `uid` cookie is `id.expiry.HMAC` signed with `RISA_SESSION_SECRET` (valid `SESSION_TTL` = 8 h; `RISA_COOKIE_SECURE=1` adds the secure flag; `RISA_PASSWORD_<ID>` env vars replace the demo passwords; `POST /login` locks an ip+username for 5 min after 5 wrong tries, in memory via `auth.login_allowed`). Hardening: chat `state.slot` is keyed by user id and also caps `RISA_MAX_PER_MIN` (20) questions a minute; `_save_upload` refuses a request folder over 200 MB, a form takes at most 10 files, files saved by a rejected form save are removed, and `extract_text` refuses a .docx/.xlsx/.pptx that unpacks over 100 MB (random at start if unset, so logins end on restart). Users: table `users (id, name, role, created, phone, faculty, avatar_color, avatar)` in `tracker.db` (the last four are the profile; added to old databases at start) (role `researcher` or `staff`, checked by the database; no passwords). The four demo accounts are seeded from `MOCK_USERS` with INSERT OR IGNORE at start, so a role changed in the table survives a restart; the mock login still checks passwords from config. `current_user` reads the table on every request (a role change applies without a new login; an id missing from the table gets 401). Every name and role check in the API (`_role`, `Tracker.role_of`, `Tracker.name_of`, also the chat's my-requests text) reads the table. Prepared for CMU login: the login callback calls `Tracker.upsert_user(email, name)` (a new person is added as researcher; a known one is left alone, so a name edited on the profile page is never overwritten by a later login) and `Tracker.set_role` makes someone staff; then drop the seeding line and `authenticate`. Profile: the header name chip is a link to `/profile` (same `home.html`; `boot` in `home.js` shows `profileScreen` when the path is `/profile`, without the bell). The page edits the person's own display name (required, 80 characters), phone (digits and `+ - ( ) .`, 20), faculty or unit (100), a colour from `AVATAR_COLORS` (six fixed values, checked by the server) or a photo, and shows id and role read-only. `GET /profile`, `PUT /profile` (never touches id or role; 400 with a Thai message when invalid), `PUT`/`DELETE`/`GET /profile/avatar`. The browser crops the photo square and shrinks it to a 256 px JPEG before upload; the server accepts only JPEG, PNG or WebP by file signature, max 300 kB, stores it as a blob in `users.avatar` and serves it with its own type, `nosniff` and `no-cache` (the page adds `?v=` to refetch after a change). `GET /me` also returns `avatar_color` and `photo`. Researchers also get the LINE card there (link with a code, or `POST /api/line/unlink`, which removes every LINE link of the user and their chat memory); the page has a logout button too. `GET /users` (was `/mock-users`) needs a login and returns id, name and role. `app/core/auth.py` holds `User`, `authenticate`, `session_value`, `current_user` and `require_staff`, the one place to swap for CMU login; both `app/features/tracker_api.py` and `app/api/admin.py` use it). Posts: staff turn on เปิดรับ for an approved type (`POST /types/{id}/publish`, owner = whoever publishes unless `owner_id` names another staff member; `POST /types/{id}/close`; columns `open` and `owner_id` on `types`, added to old databases at start). Every logged-in user can read `GET /open-types`; a researcher starts their own request with `POST /open-types/{id}/start` (their own submission from the newest approved version, titled "Type - Name", staff in charge = the owner; one request per researcher per post: starting again returns the existing request, which the researcher keeps editing by re-uploading until the document is sent). Closing hides the post and keeps existing requests. Staff delete a draft (`DELETE /versions/{id}`; the type goes too when it was its last version) or a whole type with its forms (`DELETE /types/{id}`); both give 409 while any request uses it, and remove the source files. Who sees a post: on the type page staff pick นักวิจัยทุกคน or เฉพาะคนที่เลือก with a researcher checklist (`PUT /types/{id}/audience` with `user_ids` = list or null; column `types.audience`, JSON list, empty = everyone, added to old databases at start; 400 for an empty list or a non-researcher). `GET /open-types` and `POST /open-types/{id}/start` only see posts the researcher is allowed (others get 404; staff see all); existing requests are not touched. The list badge reads เปิดรับ · N คน for a limited post. The old staff form that created a request for named researchers was removed from งานทั้งหมด (`POST /submissions` still exists). Slow AI steps show progress: the endpoints that call the model (`POST /types`, `/types/{id}/versions`, `/versions/{id}/redraft`, `/types/{id}/forms/draft`, `/submissions/{id}/uploads`, `/submissions/{id}/forms`) run through `tracker_api._progress`. Uploaded files are saved and form answers validated before the stream starts, so those errors stay plain 4xx. In the page, `apiStream` reads the lines and `runProgress` (home.js) replaces the clicked card with a checklist of finished steps and the seconds the current one has taken, with a back button on error. Online forms (table `forms`, one row per type and document: title, `fields`, status `draft` or `approved`). A field is `{key, label, hint, type, required, options}` with type text, longtext, number, date, choice or file; `validate_form` in `app/features/tracker.py` fills defaults and keeps keys stable when staff relabel. The staff tab ประเภทงาน lists types grouped under their category: each category is a fold (open when it has types, count badge) holding a table with columns name, steps, forms ready, status badge and action (every category shows, empty ones say ว่าง; types with none sit under อื่น ๆ); creating a type is a header button that opens a popup (`modal` in `home.js`). The popup offers สร้างและกรอกเอง (a name is enough: `POST /types` without a file makes a draft with one empty step and opens the step editor; no source file, so ให้ AI ร่างใหม่ is hidden and `/redraft` answers 400) or uploading a guide for the AI to draft (optional). The list is one flat table: search box, category chips (a chip filters; ✎ renames, ✕ deletes an empty category, the dashed chip adds one, and a type row dragged by its grip onto a chip moves it, `PUT /types/{id}/category`; อื่น ๆ clears the category), and a ★ on each row that pins the type (`PUT /types/{id}/pin`, `types.pinned`). Pinned types sort first here and form a ★ ปักหมุด group at the top of the researcher's เริ่มงานใหม่ list (`pinned` in `GET /open-types`). Native HTML5 drag and drop, so no touch support; category order is no longer edited in the UI (`PUT /categories/order` still exists). Web forms are switched off for now: the type page no longer shows แบบฟอร์ม, `GET /submissions/{id}` always returns `forms: {}` so every document is an upload box, and the list column shows the number of documents (the forms code and `forms.js` stay, unused). Click a type's title or its ✎ แก้ชื่อ pill to rename it (`PUT /types/{id}/name`; Enter saves, Esc or leaving the box cancels, a hint under the box says so). File formats: a step may carry `formats`, a map from one of its document names to a list of `pdf`, `docx`, `xlsx`, `pptx`, `image` (jpg, jpeg, png); missing = PDF and Word as before. `validate_steps` rejects an empty list, an unknown format or a document that is not in the step; `allowed_exts` (tracker.py) turns it into extensions and `POST /submissions/{id}/uploads` refuses any other with 400. The step editor lists one row per document (name box, a ▾ pill showing the accepted formats, ✕; Enter adds a row); the pill opens a tick list, stays grey for the PDF + Word default and turns teal when changed, at least one format stays ticked, Esc or a click outside closes it; on save blank and repeated names are dropped and default formats are not stored; the researcher's upload box filters the file picker and names the formats. The AI check reads PDF, Word, Excel and PowerPoint; an image is accepted but shows as cannot-check (no text reading yet). Each type has one page (list row, then จัดการ) with its steps and documents (แก้ไข opens the step editor on the live version: `PUT /versions/{id}` calls `Tracker.update_live`, text always editable, step count locked once a request uses the version), its forms and its เปิดรับ controls; there staff press AI สร้างฟอร์ม (`POST /types/{id}/forms/draft`; `forms_ai.draft_form` reads the type's guide file plus the document name; 502 and nothing saved if the model gives nothing usable), edit in the editor with a live preview (`PUT /types/{id}/forms`; an approved form stays approved) and approve (`POST .../forms/approve`). No Word file is made. A document with an approved form is filled in on the website: `GET /submissions/{id}` returns `forms` as `{doc: {title, fields}}` and the researcher saves answers with `POST /submissions/{id}/forms` (multipart: `doc_name`, `answers` JSON, `file_keys` + `files` for file fields; photos .jpg/.png allowed there). The server checks required, number, date and choice, stores a snapshot of label, type and value in `uploads.answers` (so later form edits never change what staff review) and runs the AI check on the answers text. Saving again replaces the answers (earlier attachments stay unless a new one is chosen) until the document is sent. Staff in charge of a request can also fill, upload and send on the researcher's behalf (other staff get 404); the request page (งานทั้งหมด, ดูรายละเอียด) lists the step's documents and lets them review a sent one (`reviewBlock`, shared with the review queue). Notifications: table `notifications` (user, request, text, seen). `Tracker._notify` writes one row for each person involved except the one who acted, when a request is created, a document is sent (staff in charge hear), reviewed (researchers hear approve or return with the note), a step advances or is moved, or the person in charge changes. `GET /notifications` returns the newest 30 and the unread count; `POST /notifications/seen` marks all read. The header bell (`mountBell` in home.js) shows the count, puts it in the tab title, checks once a minute, and opens a list whose items go to the request; it is in-app only, email comes with real login. The staff งานทั้งหมด tab lists one row per type (counts of requests, in progress, finished, waiting); a click opens that type's requests, and ← returns (the open type survives a visit to a request). It filters client-side by text, status (รอตรวจสอบ, กำลังดำเนินการ, เสร็จสิ้น) and person in charge. A return note stays on a document while the researcher edits or saves a draft (`add_upload` carries the last note). A researcher can take a sent document back (`POST /uploads/{id}/withdraw`, status returns to `screened`, staff in charge are told) and cancel their own request until any document is sent or approved (`DELETE /submissions/{id}`, 409 after); the staff in charge may delete a request at any time. Both remove uploaded files. A new type created with a blank name gets one from the AI (`_type_name`, falls back to the file name without extension and brackets). Finished requests sit in a collapsed list on the researcher home. The researcher's to-do list (`todoItems` in todo.js) covers the documents of each request's current step: returned, ready to send, not filled in or only a draft, then waiting for staff. What a researcher types in a form is also kept in this browser's localStorage as they type (not files, key per user, request and document) and restored on the next visit; it is cleared after a successful save. The AI check is a completeness and basic-logic check only (empty required parts, placeholder text, wrong format, end before start, totals that do not add up, unreadable text); it is told not to judge whether amounts, dates or reasons make sense, which is the staff's decision. AI findings are `{kind, text, field?, fix?}`: the screening prompt asks for one problem per finding, one sentence of at most 120 characters, the field concerned and a short fix, at most 8, and `screen_document` sorts them missing, incorrect, unclear. The page shows a count line, then one card per finding (label, field, sentence, suggestion); older stored findings without `field` or `fix` still render. Sent forms follow the same send, review and auto-advance flow as file uploads; staff see the answers and open attachments through `GET /uploads/{id}/answer-file?key=` (same access rules as the upload). A document with no approved form keeps the plain `.pdf`/`.docx` upload; the plain upload is refused for a document that has a form. Plain uploads: researchers upload `.pdf` or `.docx` (max 10 MB, name sanitized, stored under `uploads/`, git-ignored) for the current step; AI screens once; the researcher may send even with findings. A scanned PDF or a bad model answer gives status `cannot_check`, which can still be sent. Staff see the queue, open the file, dismiss findings, then approve or return with a note.

### Other files

- `app/api/server.py`: `/api/chat/stream` is what the page uses: JSON lines `{"status": text}` while a tool runs, `{"delta": text}` while the answer is written (`{"delta": null}` = discard it), then `{"done": true, "text", "files"}` or `{"error": text}`. It runs `answer` in a thread and relays its deltas through a queue; cache, per-IP slot, and logging match `/api/chat`. The final `text` replaces what streamed, since marker and language fixes can change it. `/api/chat` is the same answer in one JSON response (tests, evals, load test) and returns `{"text", "files": [{"id","name"}]}`. A question with no history is looked up in `state.cache` (key: lower-cased, whitespace-normalized message) before any OpenAI call.
- `app/core/state.py`: `cache` (up to `CACHE_MAX=500` replies, no expiry) is cleared by `admin.reindex`, so a changed index never serves old answers. Questions with history are never cached, and failed answers are never cached.

## 4. One request, step by step

Staff types: "ขอใบเสร็จค่าครองชีพ" (send me the living allowance receipt).

1. `/api/chat` calls `answer(history, message, store)`.
2. The model must call a tool. It calls `find_files(query="ใบเสร็จค่าครองชีพ")`.
3. `Store.find_files` returns candidates, for example `f1 | 1 - Living Allowance - Receipt.pdf | topic: CMU Presidential Scholarship | <Thai summary>`.
4. The model reads the summaries and calls `send_files(["f1"])`.
5. Code checks `f1` is a real candidate and records the doc id.
6. The model writes one Thai sentence. Code returns `Reply(text, [doc_id])`.
7. The UI shows the sentence plus a download link named after the file.

For "ลาพักร้อนกี่วัน" the model calls `search_documents` instead and answers from the chunks. If no chunk is close enough it says `NOT_FOUND`, and the user gets the HR contact message.

### Cost controls

- Embeddings are local, so they cost nothing. Summaries are one call per new or changed file.
- Chat is the recurring cost: 2 to 3 calls per question, each resending system prompt, tool schemas, history and tool results.
- Repeated first questions cost nothing (cache). Replies are capped at 600 tokens. Check real spend with the `tokens:` line printed by `python -m evals.run_eval`.

## 6. Known limits

- Eval runs are noisy. One run shows plus or minus a point or two.
- Typo request "ขอดูเอหสารทุน" is ambiguous now that two topics exist.
- "All receipts" sometimes returns only some of them.
- Spam guard: one IP may have `RISA_MAX_INFLIGHT` questions being answered at once (default 2, 0 = off); more get 429 and a Thai 'still answering' message. There is no limit on how many questions it asks over time, and cached answers are free. The page sends one question at a time, so only a script flooding the API hits this, and it caps one flooder at about 2 questions per answer time (a few seconds). Behind a reverse proxy every visitor shares the proxy's IP, so run uvicorn with `--proxy-headers --forwarded-allow-ips=<proxy ip>`, or two simultaneous users would block each other. Counts are per process.
- Chat questions run in parallel (one thread each, up to 40 in uvicorn's pool); extra ones wait in that pool. A re-index no longer blocks chat. Chat runs as one process: the answer cache is per process, so do not start several workers without moving it out.
- Image-only (scanned) PDFs are not indexed because there is no OCR.
- Spreadsheets: formulas show their last saved value (nothing if the file was never opened in Excel), charts and images are ignored, and rows past 3000 per sheet are cut. Slide images and diagrams are ignored.
- Summaries of near-identical receipt forms read alike.
- Only two topic folders exist. The topic filter is lightly tested with real data.
- No log of real staff requests exists yet. The eval set is written by hand.
- Cache has no time limit and is cleared only by reindex. Editing files in the admin without reindexing leaves old answers cached, same as the index itself.
- Cache is per process and lost on restart.
- Work is not committed yet. `content/` has uncommitted changes.
