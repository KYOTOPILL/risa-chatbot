# Defense: the fix should go ahead as described

1. **It was tested, and a bad part was thrown out.** The category-in-embedding change was tried and reverted: "Tests showed it made things worse, because all files in one topic share the same prefix... (a request for the scholarship announcement started returning receipts). It was reverted." A team that drops its own idea on evidence is not shipping blindly. The objection is that the final design is unproven at scale. But the part that was most likely to blur results is gone, and what is left is a filter, not a change to what gets embedded.

2. **The filter is soft and fails safe.** "Search inside that folder first; if nothing there is under NAME_MAX, fall back to searching all folders." A wrong category guess ("sometimes wrong") costs one extra search, not a missed file. The objection is that the filter does nothing today. That is true (concede: one topic folder, no real multi-topic test). But a no-op today with a fallback that restores the old behaviour is low risk, and a unit test with a fake store covers both the prefer and fall-back paths.

3. **The regex extension fixes a real, observed failure.** "ขอประกาศรับสมัครทุน" "was treated as a plain question and returned 'not found'." After the change it "returned only the announcement." The new words (ประกาศ, ระเบียบ, นโยบาย, สัญญา) are ordinary Thai document words, and the regex is the existing backstop for the unreliable small model. The objection is false positives on ordinary questions. The record shows none, and the request verb (ขอ, ส่ง, โหลด) must also be present.

4. **Results on the live index are precise in both directions.** One-file requests returned one file (thesis, living allowance, announcement). The "all receipts" request returned all 6. A nonexistent leave form returned nothing, which is correct. Six near-identical receipt forms are a hard case for name search, so this is a meaningful test. Concede: the all-of-topic request returned 6 of 7, and NAME_MAX and NAME_TIE were tuned on 7 files only.

5. **It is cheap to reverse and not yet committed.** The one costly step, rebuilding the index after a format change, is not needed here because the category embedding was reverted. Nothing is committed, 103 unit tests pass, and the design uses what is already built: a name index with cached summaries and incremental re-indexing. Missing from the record: any real staff requests (evals/questions.json points at deleted mock documents). That argues for logging real requests after release, not for blocking a change this small.
